# DealerPilot Architecture

> Describes the **current** architecture of the codebase.

## Architecture Layers

**One-way dependency direction for business logic:**

```
composable → store → service
component → (composable | store | service)
```

- **Service** → knows nothing about store or composable (pure API / domain / data-managing logic).
- **Store** → can use services and utility composables (e.g. VueUse), but should NOT use project orchestrating composables. Don't add a store for every view or feature — only when state is shared across multiple areas. Global stores live in `src/store/modules/` and aren't tied to a specific view or feature (e.g. `user-session.store.ts`, `general.store.ts`).
- **Composable** → orchestrator for business logic. Can use stores and services.

## Views vs Features

| Aspect              | Views                    | Features                       |
| ------------------- | ------------------------ | ------------------------------ |
| **Purpose**         | Route-bound pages        | Reusable, isolated modules     |
| **Route awareness** | Strictly tied to routes  | Route-agnostic                 |
| **Location**        | `src/views/{view-name}/` | `src/features/{feature-name}/` |

**Feature isolation rules:**

1. A feature can contain components, services, stores, and composables, but always has a single responsibility.
2. Features must NOT depend on other features directly.
3. Views, composables, and stores act as "feature managers" and orchestrate cross-feature communication. For example `views/search/Search.vue` mounts `Chat.vue` from `features/chat`.
4. For loose coupling between features (or other layers), use the **`useCustomEvent`** composable (`src/composables/useCustomEvent.ts`) — it wraps native `CustomEvent` + VueUse's `useEventListener`.

## Composable example

```ts
// Place under /features/checkout next to the CartCheckout component,
// or inside /views/checkout if it's view-specific.

export function useCartCheckout() {
  const loading = ref(false);
  const cartStore = useCartStore();
  const checkoutStore = useCheckoutStore();

  async function checkoutProducts() {
    loading.value = true;
    try {
      const products = await cartStore.getProducts();
      await checkoutStore.checkout(products);
    } finally {
      loading.value = false;
    }
  }

  return { checkoutProducts };
}
```

## Types & Enums

- **`<name>.d.ts`** — colocated TypeScript declarations (interfaces, type aliases) for the feature/view. Import explicitly with `import type { I…, T… } from '@/features/<feature>/<name>.d'`. Truly cross-cutting types live in `src/types/`.
- **`<name>.enums.ts`** — colocated enums for the feature/view. Enums in both `src/features/**/*.enums.ts` and `src/views/**/*.enums.ts` are auto-imported globally.
- Naming follows the global ESLint convention: interfaces start with `I`, type aliases with `T`, enums with `E`.

## VueUse & Element Plus First

Before building from scratch, check existing libraries:

- **Composables** → check VueUse first (state, browser APIs, sensors, animations, utilities).
- **UI components** → check Element Plus first (buttons, forms, tables, dialogs, etc.).

## Auto-Imports

Configured in `vite.config.imports.ts` (scripts) and `vite.config.components.ts` (components). Type declarations are written to `dts/auto-imports.d.ts` and `dts/components.d.ts`; ESLint globals come from `.eslintrc-auto-import.json`. **All three files are auto-generated — do not hand-edit.**

Auto-imported as values:

- Vue, Vue Router, Pinia, VueUse APIs.
- `useQuery`, `useMutation`, `useQueryCache`, `defineQuery`, `defineMutation`, `defineQueryOptions` from `@pinia/colada`.
- `dayjs` from `@/plugins/dayjs.plugin.ts`.
- Everything in `src/composables/` and `src/{features,views}/**/composables/`.
- All `src/store/modules/*.ts` and `src/{features,views}/**/*.store.ts`.
- All `src/services/*.ts` and `src/{features,views}/**/*.service.ts`.
- All `src/{features,views}/**/*.queries.ts` (Pinia Colada query/mutation factories).
- All `src/{features,views}/**/*.enums.ts`.

Auto-registered as components:

- `src/components/**`, `src/components-v2/**`, `src/layouts/**`.
- Every `src/{features,views}/**/components/` and `**/components-v2/` directory.
- Element Plus components via `ElementPlusResolver`.
- Phosphor icons via the `Ph` prefix resolver (e.g. `<PhCar />`).

Custom `.ts` / `.json` imports outside these paths still need explicit imports.

## Server-state with Pinia Colada

`@pinia/colada` is the standard server-state layer. Define queries and mutations in `<name>.queries.ts` files next to the feature/view; they are auto-imported. `PiniaColadaDevtools` is mounted in `App.vue`.

## HTTP & Error Handling

- The axios client lives in `src/services/http/` with request and response interceptors.
- The response interceptor handles global concerns (Sentry logging, `ElNotification`, 401 redirects). Do not duplicate `ElNotification` inside individual service catches.
- For per-request behavior (e.g. silencing the global notification), pass a config flag through the interceptor (such as `showNotification: false`) rather than wrapping each call.

## Routing

- All routes resolve through `src/router/routes.ts`, which composes feature/view `*.routes.ts` files.
- Always navigate with `routeNames.xxx` — never path strings.
- Route name **values** are camelCase. The `routeNames` object is generated by a Vite plugin from `routeNames.xxx` usage in code, so a new key becomes available without manually editing a constants file.
- Guards live in `src/router/guards/`; the global chain is wired in `src/router/index.ts`.
- Root view component filename matches the route name (e.g. `Login.vue` → `routeNames.login`).

## Modals

- Create modal components ending in `Modal.vue` (auto-registered).
- Drive them with the `useAppModals()` composable: `openModal('SomeModal', props)` / `closeModal('SomeModal')`.
- The modal host is the `<Modals>` component rendered once in `App.vue`.

## Icons

Two icon libraries are present, but **Phosphor is the standard going forward**. FontAwesome is legacy and being removed — do not introduce new FontAwesome icons.

Use Phosphor via auto-imported `Ph*` components, e.g. `<PhCar />`, `<PhUser :weight="'duotone'" />`.

## Styling

- TailwindCSS first; semantic colors (`primary`, `success`, `warning`, `danger`, …) and the project spacing scale live in `tailwind.config.js`.
- Component-scoped SCSS in `.vue` files for anything Tailwind can't express cleanly.
- Global stylesheets live in `src/assets/styles/` (notably `element-reset/` for Element Plus overrides).

## Naming Conventions

- Folders: `kebab-case` (e.g. `user-profile/`).
- Vue components: `PascalCase` (e.g. `UserProfile.vue`); prefix `App` when the bare name would clash with an HTML tag (`AppButton`, `AppTable`).
- TS files: `kebab-case` with suffix — `*.service.ts`, `*.store.ts`, `*.queries.ts`, `*.routes.ts`, `*.utils.ts`, `*.enums.ts`, `*.d.ts`.
- TypeScript: **`I` prefix for interfaces, `T` prefix for type aliases, `E` prefix for enums** (enforced by `@typescript-eslint/naming-convention`).
- Routes: `routeNames` keys in camelCase; URL paths in kebab-case.

## Hard Rules

- **Never** `export default` — always named exports.
- **Never** `as any` to silence TypeScript — fix the underlying type.
- Services must not import stores or composables.
- Stores must not import project orchestrating composables (VueUse-style utility composables are fine).
- Features must not depend on other features. **Only exceptions:** a feature may import another feature's Vue components, types, and enums. Everything else (stores, composables, services, queries, utils) is off-limits across feature boundaries — if you need to share that, lift it into `shared/`.
- All Vue components use `<script setup lang="ts">`.
- Page/component CSS goes in `.vue` files; only general styles belong in `src/assets/styles/`.
